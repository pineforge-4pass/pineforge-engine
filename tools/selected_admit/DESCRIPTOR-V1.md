# DESCRIPTOR-V1: request descriptor, manifest and argv/I-O contract of `pineforge-selected-admit`

This file specifies the request descriptor, the result document, the build manifest and the argument and descriptor-passing contract of the `pineforge-selected-admit` helper. Its sha256 is taken at configure time and compiled into the manifest as `descriptor.spec_sha256`, so the committed bytes are the ones the digest binds; a test of the helper must compute the same digest from the committed file itself, never from the helper's own output. The status label inside the text (PROPOSAL) is the label the decisions carried when the text was written. No file descriptor number is fixed here: the descriptor and every stream are passed as parameters. In this file "the App" means the application that runs the helper and maps its result.
----------------------------------------------------------------------
## 4. Descriptor and manifest schema (all PROPOSAL)
**4.1 Versions and the unknown-version rule.** Request `pineforge-selected-capacity-request/v1`; result `pineforge-selected-capacity-result/v1`; manifest `pineforge-selected-capacity-helper-manifest/v1`. The helper parses the document, then reads `schema` FIRST: any other value (v0, v2, wrong case, missing, not a string) exits 40 before any other member or any stream byte is read. Duplicate keys, unknown members, JSON numbers, nulls and trailing bytes exit 41. No default fills an omitted member. There is no "immutable" member: immutability is checked (5.2), never declared.

**4.2 Request descriptor.** Every integer is a canonical decimal string `0|[1-9][0-9]*` in uint64 range (signed for the three time fields), so no JSON number grammar exists.

|---|---|---|---|---|
| `schema` | string | yes | n/a | exactly the request string; read first |

**4.4 Build manifest** (generated at install from the installed bytes). Members: `schema`; `helper.{name,path,bytes,sha256}`; `engine.{version_full,version,git_sha,dirty}`; `descriptor.{request_schema,result_schema,spec_sha256}`; `failure_catalog.{codes[5],catalog_sha256}`; `stages`. `git_sha`, `version_*` come from `<pineforge/version.h>` (ENG:include/pineforge/version.h.in:20-23); `dirty` from the configure-time CMake variable (ENG:cmake/PineForgeVersion.cmake:113) passed to the target as a compile definition; `catalog_sha256` is the digest of ENG:docker/run_failure_codes.json and `spec_sha256` the digest of `tools/selected_admit/DESCRIPTOR-V1.md` (this file), both taken at configure time and compiled in. Per N12 (decided) the candidate build's `git_sha` is 12 or more hex digits (or the full head) and `dirty` is its flag, both supplied through the identity input, that is the file given to `CMAKE_PROJECT_INCLUDE` with `set(PINEFORGE_VERSION_GIT_SHA "<sha>")` and `set(PINEFORGE_VERSION_DIRTY ON|OFF)` (ENG:scripts/build_prebuilt_bookworm.sh:154-155,:167-168); a build with a shorter or `unknown` value still writes its manifest and records the value as it is, and the helper compiled with it refuses every descriptor (exit 40, 4.2). Each member is checked by T23 against an oracle the test computes or reads itself, never against the helper's own output. `--describe` prints the COMMON PROJECTION of the manifest: every manifest member EXCEPT `helper.bytes` and `helper.sha256` (a binary cannot embed its own digest), with the remaining members in the manifest's own order and the same canonical JSON text, so that "the manifest without those two members" and the `--describe` output can be compared byte for byte; no other member is added, dropped or recomputed by `--describe`. The App-owned checks: `helper.sha256` and `helper.bytes` equal the digest and size of the file it will exec, computed by the App from that file and never read back from the helper; the `--describe` output equals the projection of the manifest; `engine.git_sha` is consistent with the candidate head named for the build; `descriptor.request_schema` equals what its forwarder emits.

## 5. Argv and I/O contract (all PROPOSAL)
**5.1 argv.** Any other form exits 2 with usage text on stderr and no document.
```
pineforge-selected-admit --describe
pineforge-selected-admit --stage source   --descriptor-fd D --descriptor-sha256 H
pineforge-selected-admit --stage selected --descriptor-fd D --descriptor-sha256 H
```
D is a decimal number >= 3. H is the SHA-256 of the descriptor bytes as the App computed them. D, every stream fd and every `forward_fd` are PARAMETERS. The App's interface fixes none of them for the helper: the App's own descriptors, among them its fd 3, 4 and 5, are none an alias of another and none a helper input.
**5.2 How input arrives.** Paths are never accepted.
- (a) Descriptor: D is an open regular file or memfd, read with `pread` from 0, at most cap+1 bytes (cap 262144, N10), ONCE into one buffer (read-one-past, cf. ENG:docker/request_feed_inventory.py:159-172; a short `pread` is continued from the first unread offset and EINTR is retried until cap+1 bytes or EOF, and any other `pread` error is exit 41 `descriptor_invalid`); that buffer is hashed and compared with H before any parse. A mismatch is exit 41. This is BYTE-SNAPSHOT VERIFICATION: agreement with H authenticates exactly the bounded bytes the helper read; it does not make D an immutable file descriptor and says nothing about a writer's lifetime. The helper parses the descriptor and takes every value it uses from that same verified buffer; it never reads D a second time (a second read would be an unverified second snapshot). The immutable lifetime of the closed stream files, consumer replay and extent authority are NOT provided by this digest; they stay N4, N5 and E8c. No immutability member is added to the descriptor or the result.
- (b) Stage `selected`: each stream is a read-only regular file read with `pread` in 64 KiB chunks from offset 0, so no shared offset moves. Preflight before any read: `fstat` size equals the declared extent, `F_GETFL` read-only, not a directory. At the extent: probe one more byte (must be EOF), `fstat` again (device, inode, size, mtime, ctime unchanged), SHA-256 equals the declared digest, and only then EOF is reported to the reader. On a refusal or error before EOF the unread tail is not hashed and the document says `custody_complete:false`: a refusal is then only as authentic as the bytes already read; the rest is the App's immutability proof (N4).
- (c) Stage `source`: read end `fd`, write end `forward_fd`; memory does not grow with the input: it is bounded by the record cap and one 64 KiB chunk: the record window and the reader's copy of one field (each up to `max_record_bytes`), the chunk and the process base. No multiple of `max_record_bytes` is promised. The record window (the octets the reader consumed for the current record, kept until its observers return, 5.2 (f)) is reserved at `max_record_bytes` (ENG:src/selected_capacity_source_stage.cpp:26), and the CSV reader keeps its own copy of the field it reads, up to `max_record_bytes`, appended one octet at a time (ENG:src/selected_capacity_csv_reader.cpp:218-219,:239); a string that grows can hold its old and its new buffer at once. Measured peak resident set, with `max_record_bytes` = 1 MiB and one record of exactly that size, over a small record: +2.85 MiB in stage `source` and +1.73 MiB in stage `selected`, on a process base of about 4 MiB; only that size was measured, on one build and one host. A custody violation inside either stage is an exception from the streambuf; the reader sees badbit (ENG:src/selected_capacity_csv_reader.cpp:161-163,:173-175), and the helper reports its recorded reason, not a generic I/O error.
- (d) Hygiene as ENG:docker/run_json.py:6070-6077: every number >= 3, all distinct from each other and from D. One inode may appear in two entries only as distinct fds with distinct roles (ENG:src/selected_capacity_driver.hpp:36-38); otherwise exit 41. In stage `source`, when the stage is active (it carries `source_rows` or `bytes`; otherwise exit 10 `helper:no_stage_fields` comes first), a `forward_fd` that is a pipe write end and the same file as the helper's stdout (fd 1) or stderr (fd 2), compared by device and inode before any read (so another open of the same FIFO counts too), is refused with exit 41 (`helper:descriptor_invalid`, `where.input_id` the stream): stdout carries the one result document and stderr the human text, and forwarded octets must not enter either. A `forward_fd` that is not a pipe write end is refused earlier, with exit 33, and a standard stream that cannot be examined with `fstat` (a closed descriptor, for example) is not compared.
- (e) The helper never writes a file. It writes stdout once (the result), stderr (human text, never parsed) and, in stage `source`, `forward_fd`. It ignores SIGPIPE so EPIPE is an error return. Environment and files: every process reads `GLIBCXX_TUNABLES` once at start (the C++ runtime of the measured build, libstdc++ from GCC 13.3 on glibc 2.39, on aarch64; observed on every path, and no other C++ runtime was measured). Stage `selected` runs the calendar when the `script_bars` bound is present (ENG:src/selected_capacity_driver.cpp:335). For a UTC-like zone (the empty name, `UTC`, `GMT`, `Etc/UTC`, `Etc/GMT` or a zero offset) it reads nothing more. For a fixed non-zero offset such as `UTC+5` it reads `TZ` and, unless `TZ` already holds the normalized target (`UTC-5` for `UTC+5`: the POSIX sign is the opposite), sets `TZ` in its own environment (it never restores it) and calls `tzset`; in the measured runs the C library then made one failing open of a zone file named by the normalized target (`UTC-5` for `UTC+5`, `UTC+3:30` for `GMT-3:30`), and when `TZ` already holds the target neither `setenv` nor `tzset` runs. A POSIX rule string (`TzClass::Posix`, ENG:src/native_calendar.cpp:1100-1103) takes the same `TZ` and `tzset` path; its file opens were not measured. A zone given by name (an IANA name, a name with a leading colon or a name with a slash) takes that `TZ` and `tzset` path as well (the measured runs read `TZ` and `TZDIR` and set `TZ` to the name), and it also resolves a zone database root: on glibc a non-empty `TZDIR` is the root and an unset or empty one means `/usr/share/zoneinfo`; on Darwin `TZDIR` is ignored and the root is `/var/db/timezone/zoneinfo`, or `/usr/share/zoneinfo` when that directory cannot be resolved as a directory; on any other libc `TZDIR` is ignored and the root is `/usr/share/zoneinfo`. It opens the zone file under that root read-only, through descriptors of its own (ENG:src/native_calendar.cpp:811-835,:905-923, ENG:src/timezone.cpp:91-127). The helper creates and writes no file: that is read from the code of the helper and of the engine units it links; the import-list test, which lists 41 function names and rejects 39 of them (it allows the two the helper links, `dlopen` and `recvmsg`), does not check it, because none of its names is a file function. A root that is not a directory (on glibc, a non-empty `TZDIR` that names no directory) or that holds no such zone makes the zone unsupported (exit 11, `calendar_unsupported`, `where.option` `engine_timezone`), except that a bare name that is also accepted by the helper's own POSIX-rule check, such as `EST5EDT`, is accepted as a POSIX rule whenever no usable zone file is found for it (for example a root that is not a directory, an absent file, or content that is not a zone file), so the result depends on the host's time-zone database, which neither the result nor the manifest records. System calls: a short `read` or `pread` is continued and EINTR is retried (the four-octet read of a zone file's magic number is a single `read` with no retry: a short read or an error makes the zone unsupported at admission, exit 11, with the exception stated above for a bare name that is also accepted by the helper's own POSIX-rule check); a `write` of the result or to `forward_fd` continues from the first unwritten octet after a partial count and retries EINTR; on EAGAIN (a non-blocking descriptor) the helper waits with `poll` for POLLIN or POLLOUT, with no timeout of its own (the App's timeout and kill handling bound the wait, N1), and retries; any other write error, EPIPE included, is `helper:result_write_failed` (result) or `helper:forward_write_failed` (`forward_fd`), exit 32, and any other read error on an input stream is `input_read_failure`, exit 32 (an error of the descriptor `pread` other than EINTR is exit 41, 5.2 (a)). Stage `source` forwards one admitted record at a time, the header first: a record is written to `forward_fd` as one complete write sequence after its observers return and before the helper consumes the next octet of that stream (a read ahead of up to one 64 KiB chunk may already have been taken from the producer), and is never batched with the next record, so every admitted record has been written to the pipe, for the App's drain (N1) to read, before the helper waits on a read from the producer, and the bound of T14 holds per record.
- (f) Record cap (`limits.max_record_bytes`, M). A RECORD is exactly what `CsvReader` consumes in one call of `read_header()` or `next()`, tokenized as the reader tokenizes (ENG:src/selected_capacity_csv_reader.cpp:218-260); its length is the number of octets it consumes, the figure the reader reports as `csv_bytes` (hpp:47-48): every delimiter and the whole terminator count. A record ends at LF, CRLF or CR outside quotes, or at EOF; a quote that opens a field makes LF, CR and comma data until its closing quote, a doubled quote is one data quote, an unclosed quote runs to EOF, and a quote anywhere else in a field is data (cpp:220-239). A record is too long when its length would exceed M; a record of exactly M octets passes. The cap is enforced per octet before the octet reaches the reader, in BOTH stages, so the reader's field string never holds more than M octets: `FdStreambuf` keeps its get area empty, so every consumed octet passes `uflow()` and a peek passes `underflow()` only, and a `RecordTracker` fed by `uflow()` mirrors the reader's state (field start, unquoted, quoted, quote seen inside quotes, after a CR outside quotes: a following LF is the second octet of that terminator and belongs to the same record, any other octet opens the next record). When the next octet would be the (M+1)-th of the current record, `uflow()` records `CustodyReason::RecordTooLong` and throws without delivering it; the reader sees badbit and the helper reports `input_error` / `helper:record_too_long`, exit 31, not the native `io_error` of exit 32. The reason `helper:record_too_long` therefore means one thing: a record, tokenized as above, is longer than M octets; no format judgment was made on it. The document carries `where.input_id` and `where.row_index` (the header is 0). A peeked octet is never counted. The reader's peek after a CR (cpp:252) means a lone-CR record is complete only when the next octet or EOF is available, and stage `source` forwards it then. `run_driver` offers no per-record hook (driver.cpp:341-360, :282-285), so stage `selected` has no per-record reset and the tracker is its only mechanism; stage `source` owns the loop but uses the same tracker and additionally checks, per record, that the window it kept holds exactly the `csv_bytes` the reader reported, a disagreement being exit 70 and never a silent pass. M bounds one record; it bounds neither a stream, nor the `bytes` bound, nor the number of records.
- (g) `bytes_read` (per stream, in the document of a refusal or an error) is the number of octets of that stream the reader consumed: the sum of the `csv_bytes` of its header and of every record it consumed, including the record that crossed a bound and, for a record refused by (f), the octets delivered before the refused one; it is counted in `uflow()`, never from `pread` or `read` sizes or from chunk read-ahead, and a peeked octet is not counted. Hashing is chunk-granular and is reported only through `custody_complete`. `FdStreambuf` allocates its 64 KiB chunk at the first read of its stream and frees it at EOF or on destruction, so the 256 streams of a descriptor hold at most the chunk of the stream being read.
**5.3 Output document.** One JSON line on stdout, ASCII, fixed key order, uint64 as decimal strings, `exit` echoing the process status, byte-identical for identical inputs. Keys: `schema, exit, stage, outcome, status, reason, identity, descriptor_sha256, helper{git_sha,request_schema}, custody_complete`. `status` and `reason` carry the native `DriverStatus` and `DriverReason` enumerator names in snake case (ENG:src/selected_capacity_driver.hpp:57-88) so no distinction is lost, or a helper-only reason marked `helper:`. Exits 0, 10, 11, 30, 31, 32 and 34 add `state` and `coverage` (hpp:90-137). Exits 21 to 25 add `code, class, retryable, args` (from `RunFailureValue::args`, already canonical), `english` (`what()`), `where.input_id` and per-stream `bytes_read` (the octets the reader consumed, 5.2 (g)), but no state or coverage, because the exception carries none. Stage `selected` adds `sink{kind:"counting",bars,first_ts_ms,last_ts_ms}`, also on a refusal, where `bars` is the number of Bars COUNTED before the throw, not Bars delivered to any consumer (E8c option 2: the sink retains nothing); stage `source` adds `forwarded_bytes`, `forward_sha256` and `deferred` (the bounds it cannot see: primary_rows, script_bars, auxiliary_rows and the cross-role part of bytes). A missing, garbled or exit-disagreeing document is an internal error, never an admit (idiom ENG:docker/selected_window_plan.py:47); an EOF on a forward pipe is complete only with exit 0 and `forwarded_bytes` equal to what the App's writer received (App implements).
